# 后台响应采集改动评审说明

> **编写时间**：2026-06-01；**修改时间**：2026-06-01；**使用模型**：GPT-5 Codex；**用户**：Jsmond2016

---

## 背景

当前工作区未提交改动主要集中在响应体采集、响应快照清洗，以及后台侧的调试排查能力上。

这批改动涉及 3 个文件：

- `public/page-network-hook.js`
- `src/lib/quick-copy/response-rules.ts`
- `src/pages/background/index.ts`

整体目标可以概括为：

1. 保留更多“原始响应结构是否有内容”的信号，避免数组在清洗后被误判为空
2. 把 `fetch` 请求也纳入后台请求跟踪范围
3. 增加后台侧日志，便于排查“响应没匹配上请求”或“异常规则未命中”的问题
4. 给运行时 session cache 增加版本控制，避免旧缓存影响新逻辑验证

## 改动拆解

## 1. 数组清洗逻辑调整

涉及文件：

- `public/page-network-hook.js`
- `src/lib/quick-copy/response-rules.ts`

原有逻辑里，数组会先递归清洗，再过滤掉 `undefined` 项。

问题在于：

- 如果原数组本身有内容
- 但数组里的元素在递归清洗后全部变成 `undefined`

最终结果会退化成空数组 `[]`。

这会丢失一个重要信号：原始响应里“这个数组字段原本是有元素的”，只是这些元素不适合被保存在快照中。

当前改动后的行为是：

- 清洗后仍有有效元素：返回清洗后的数组
- 原数组有内容，但清洗后没有保留任何元素：返回 `[null]`
- 原数组本身为空：仍返回 `[]`

这样做的意义是：

- 保留“原始数组非空”的事实
- 避免后续规则判断或调试时，把“有数据但被裁剪掉”误看成“接口真的返回空列表”

## 2. 运行时缓存增加版本号

涉及文件：

- `src/pages/background/index.ts`

本次在后台的运行时 session cache 中新增了 `version` 字段，并引入：

- `RUNTIME_CACHE_VERSION = 2`

持久化时会把版本写入缓存；恢复缓存时会先检查版本。

如果版本不一致，当前逻辑会：

- 删除旧的 `quick-copy-runtime-session-cache`
- 放弃继续 hydrate

这样做主要是为了避免：

- 旧结构下缓存的请求记录继续参与新逻辑判断
- 调试期间由于缓存残留，出现“代码已改但现象没变”的干扰

## 3. 后台开始跟踪 `fetch`

涉及文件：

- `src/pages/background/index.ts`

`TRACKED_RESOURCE_TYPES` 从仅包含 `xmlhttprequest`，调整为同时包含：

- `xmlhttprequest`
- `fetch`

这意味着后台侧的 `chrome.webRequest.onBeforeRequest` 将会把 `fetch` 请求也写入运行时请求记录。

改动意图很明确：

- 之前如果页面主要使用 `fetch`
- 那么注入脚本回传的响应体即使拿到了，也可能因为后台里没有对应的请求记录而无法匹配

把 `fetch` 纳入跟踪后，`applyCapturedResponse` 匹配成功的概率会更高。

## 4. 增强响应匹配与规则判断的调试日志

涉及文件：

- `src/pages/background/index.ts`

### 新增 `getResponseDebugSummary`

新增了一个轻量调试辅助函数，用来从响应快照中提取：

- `data.list.length`
- `data.pagination` 的存在状态

当前返回结构类似：

- `listLength`
- `paginationState: missing | null | present`

这说明本次排查重点很可能是某类列表接口，尤其是：

- 返回了列表数据
- 但分页信息缺失、为 `null`，或规则判断与预期不一致

### 未匹配到请求时打印日志

当注入脚本回传响应体后，如果 `applyCapturedResponse` 没有找到匹配的 request record，当前会在满足摘要条件时打印日志，包括：

- `tabId`
- `url`
- `method`
- `startedAt`
- `completedAt`
- 响应摘要
- 原始响应

这类日志主要用于确认：

- 响应是否确实被注入脚本捕获到了
- 为什么后台请求列表里没有对应记录
- 时间戳或请求类型是否导致了匹配失败

### 匹配成功时打印规则命中信息

当找到匹配请求后，当前逻辑会先：

1. 生成 `responseSnapshot`
2. 用 `getMatchedResponseErrorRules(...)` 计算命中的异常规则
3. 再打印调试日志

日志内容包括：

- request 基本信息
- 状态码
- 摘要信息
- `matchedRules`
- `rawResponse`
- `responseSnapshot`

这类日志可以帮助评审和调试时直接判断：

- 清洗后的响应快照长什么样
- 当前规则到底有没有命中
- 未命中的原因是规则问题，还是快照结构问题

## 5. `applyCapturedResponse` 的处理顺序更明确

涉及文件：

- `src/pages/background/index.ts`

原逻辑是在构造下一份请求记录时，内联地计算 `responseSnapshot`。

当前则改为：

1. 先单独得到 `responseSnapshot`
2. 基于该快照生成调试摘要和命中规则
3. 再把结果写回请求记录，并执行 `withRequestAbnormalState(...)`

这样做的直接收益是：

- 调试链路更清楚
- 同一份 `responseSnapshot` 被复用，减少理解成本
- “日志看到的快照”和“实际落库的快照”保持一致

## 当前改动想解决的核心问题

从现有变更推断，这批代码很可能是在处理下面一类问题：

- 页面请求是 `fetch` 发起的，后台没跟踪到，导致响应无法回填到请求记录
- 响应里实际存在列表数据，但在快照清洗后看起来像空数组，影响异常规则判断
- 某些列表接口的 `pagination` 字段缺失或为空时，现有规则命中结果和预期不一致
- 调试时无法快速判断问题出在“请求没匹配到”还是“规则没命中”

## 评审建议重点

后续评审时，建议重点确认下面几项。

### 1. `[null]` 作为占位值是否会影响现有规则

需要确认：

- 现有响应异常规则是否把 `[null]` 当成“有内容”
- 是否会出现原本应判空的场景，现在因为 `[null]` 被误判为非空

尤其要关注：

- `data.list`
- 嵌套列表字段
- 依赖数组长度或 truthy / falsy 的规则表达式

### 2. `fetch` 纳入跟踪后是否会引入重复记录

需要确认：

- 某些请求是否会同时以不同事件形态出现
- 当前 `requestId + startedAt` 的记录生成方式是否仍然稳定
- popup 请求历史是否会因为多记录而出现噪音

### 3. 匹配窗口是否足够稳健

当前匹配条件仍依赖：

- `url`
- `method`
- `startedAt` 与 payload 时间差不超过 15 秒

如果同一页面短时间内连续请求同一接口，需要确认：

- 当前“按最接近时间排序”的策略是否足够稳定
- 是否还会把响应回填到错误的 request record

### 4. 调试日志是否需要后续降噪

当前日志会在命中特定响应结构时输出较多内容，包括：

- 原始响应
- 清洗后的响应
- 命中规则列表

这对排查问题很有帮助，但后续合并前需要考虑：

- 是否保留到正式代码
- 是否增加开关控制
- 是否会在高频接口场景下产生过多 console 输出

## 建议的验证方向

如果后续需要继续验证这批改动，建议覆盖下面几类场景：

1. 页面通过 `fetch` 发起接口请求，确认 popup 能看到对应请求记录
2. 响应中 `data.list` 原本非空，但元素在清洗后会被裁剪，确认最终快照变为 `[null]`
3. 响应中 `pagination` 分别为缺失、`null`、正常对象时，确认日志和规则命中是否符合预期
4. 同一接口在短时间内连续请求多次，确认响应是否回填到正确记录
5. 升级代码后保留旧 session cache，确认后台会自动清理旧 runtime cache

## 结论

这批未提交改动不是一次大重构，而是一次围绕“响应采集准确性”和“异常规则排查能力”的定向增强。

它的主线很清晰：

- 让后台能接住更多真实请求
- 让响应快照保留更多结构信号
- 让规则判断过程更容易被观察和解释

如果后续评审发现行为符合预期，这份改动可以作为后续继续完善响应异常识别的基础。
