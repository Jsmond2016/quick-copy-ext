# Popup Apifox 性能问题记录

## 背景

在插件支持 Apifox 接口映射后，用户反馈 popup 打开明显变慢。

当前使用场景中，Apifox 本地导出的 OpenAPI 数据量较大，默认可能包含约 2000 个接口。popup 每次打开时，如果触发了 Apifox 数据准备流程，就会带来明显的等待感。

## 问题现象

- 打开 popup 时首屏出现卡顿
- 用户主观感受是 “每次打开都很慢”
- 当 Apifox 导出数据量较大时，问题更明显

## 根因分析

问题不只是 “Apifox 数据大”，而是 popup 生命周期里做了不该在首屏做的工作。

旧实现存在两个性能风险：

1. popup 初始化时会主动检查并在必要时刷新 Apifox 数据
2. popup 侧存在本地 fallback 逻辑，可能再次执行 `fetch -> response.json() -> 遍历 paths -> 构建映射`

这意味着在最差情况下，用户每次打开 popup，都可能触发一次大 JSON 的：

- 网络读取
- JSON 解析
- 全量遍历
- 中间对象构建

对于 2000 条左右的接口数据，这些工作放在 popup 打开路径上是不合理的。

## 设计原则

针对这类数据，popup 的职责应该是“消费缓存状态”，而不是“负责准备大数据”。

更合理的原则是：

- Apifox 原始导出数据不在 popup 内长期保留
- 内存中只保留匹配所需的最小字段
- popup 打开时只读取状态，不主动做重解析
- 真正的刷新动作只在显式保存配置或手动点击刷新时执行
- 保存配置本身不应被大数据刷新阻塞

## 优化方案

本次调整采用以下策略：

### 1. 只保留最小索引结构

Apifox 导出数据加载后，不保留完整 schema，也不保留多余字段，只保留：

- `method + path -> apifoxUrl`
- `path -> apifoxUrl`

也就是两个内存索引：

- `endpointMap`
- `pathMap`

这样可以把运行时匹配所需的数据压缩到最小。

### 2. popup 启动只读取状态

popup 初始化时不再主动刷新 Apifox 数据，只读取后台已有缓存状态：

- 已就绪则显示已缓存条数
- 未就绪则提示用户手动刷新或保存配置

这样可以把首屏性能和大 JSON 解析彻底解耦。

### 3. 去掉 popup 端的大对象 fallback

popup 不再自己维护一套本地 Apifox 缓存，也不再承担大数据解析职责。

这样可以避免：

- 重复的内存占用
- 重复的 JSON 解析
- popup 与 background 双份缓存

### 4. 解析阶段直接构建索引

原来的处理方式是：

1. 遍历 schema 生成 `endpoints[]`
2. 再把 `endpoints[]` 二次写入 `Map`

现在改为在遍历 schema 时直接写入 `Map`，避免中间数组，降低刷新时的峰值内存和一次额外遍历成本。

### 5. 保存配置后后台异步刷新

最初版本里，保存设置时会同步执行 Apifox 刷新：

1. 点击保存
2. 立即请求本地 Apifox 导出地址
3. 解析大 JSON
4. 构建索引完成后才结束保存流程

这会带来两个问题：

- 保存按钮响应慢
- 用户会误以为“设置保存卡住了”

当前实现已经调整为：

1. 先立即保存设置
2. 立即关闭设置面板并让普通配置生效
3. 在后台异步刷新 Apifox 缓存
4. 刷新完成后再更新状态提示

这样处理后，`monitoredOrigins`、`apiPrefixes`、`customFields` 等轻量配置可以立即生效，而 Apifox 这类重任务被移到非阻塞路径中执行。

这一步优化的价值不只是减少 popup 打开耗时，也改善了“保存设置”的交互体感。

## 结论

这次问题说明一个明确原则：

> popup 是高频打开的交互入口，任何重量级数据准备工作都不应该放在 popup 首屏路径中。

对于 Apifox 这类大体量数据，正确做法不是单纯“把对象变成 hashMap”，而是同时满足下面两点：

- 数据结构最小化
- 计算时机后移

并且在交互层面还需要补充第三点：

- 重任务异步化，避免阻塞用户主流程

只有同时做到这三点，才能真正改善 popup 打开速度和设置保存体感。

## 后续建议

如果后面仍然需要继续优化，可以考虑：

1. 为 Apifox 缓存增加版本或时间戳信息，减少不必要刷新
2. 如果接口数量继续增大，可评估更轻量的序列化缓存格式
3. 为 popup 首屏增加简单的性能埋点，便于后续量化优化效果
4. 如果后续需要更强一致性，可考虑增加后台刷新中的状态枚举，例如 `idle / refreshing / ready / error`
