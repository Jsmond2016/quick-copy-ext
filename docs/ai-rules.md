# AI Rules

本文件定义 AI 在本仓库中的推荐协作规则。

目标不是限制修改，而是让修改更稳定、更可理解、更贴合当前项目。

## 总原则

### 1. 先完成任务，再优化形态

如果用户要修 bug、补功能或调整交互，优先完成目标，不要默认把任务升级成一次大型重构。

### 2. 以最小必要改动为默认策略

默认优先：

- 小步修改
- 局部验证
- 最少新增抽象
- 最大程度复用现有代码

只有在以下情况下才主动扩大改动范围：

- 现有结构明显阻碍需求实现
- 文件职责严重混杂
- 重复逻辑已经影响维护
- 用户明确要求重构或整理结构

### 3. 重构要“行为稳定 + 边界更清楚”

如果做重构，至少要满足两件事：

- 行为尽量不变
- 重构后的结构更容易解释

如果只是把一个文件拆成多个文件，但职责仍然混乱，这不算有效重构。

## 代码修改规则

### 1. 共享逻辑优先复用

动手前优先检查：

- `src/lib/quick-copy.ts` 中是否已有相似工具
- 现有类型是否可以复用
- popup 是否已经有对应的 service / util / component 可扩展

避免为了一次小改动复制一份近似逻辑。

### 2. 新逻辑的落点要符合职责

建议落点如下：

- 视觉展示：`components`
- 页面状态编排：页面组件或页面级 hook
- runtime / tabs / storage 通信：`services` 或共享层
- 字符串处理、对象映射、格式化：`utils` 或 `lib`
- 类型与默认值：`types` / `constants`

### 3. 不要过度抽象

以下场景不建议立刻抽象：

- 只使用一次的简单 JSX
- 很短且上下文强耦合的逻辑
- 还看不出稳定模式的两三段相似代码

优先让代码直接、可读。

### 4. 类型要明确

- 不轻易引入 `any`
- 新增运行时协议时，优先补类型
- 对外传递的对象结构尽量明确
- 对可能失败的分支保留清晰错误信息

## popup 相关规则

### 1. popup 首屏路径保持轻量

不要在 popup 打开即执行以下重任务，除非业务必须：

- 大对象解析
- 大 JSON 网络拉取
- 全量索引构建
- 长耗时同步刷新

### 2. popup 优先按职责拆分

如果 popup 代码膨胀，优先考虑拆成：

- 页面编排
- UI 组件
- service
- util
- hook

而不是继续往主文件里堆 handler 和 JSX。

### 3. 用户可见文案要可执行、可理解

避免模糊表达，例如：

- “操作失败”
- “有点问题”
- “请稍后再试”

更好的方式是说明：

- 当前在做什么
- 为什么失败
- 用户下一步可以怎么做

## background 相关规则

### 1. 改消息协议要成对修改

如果调整 runtime message：

- 请求类型要同步
- 响应类型要同步
- popup 调用方要同步
- 文档最好同步补充

### 2. 改缓存逻辑要注意 tab 维度和兼容性

后台逻辑通常和 tab、请求记录、缓存状态绑定，改动时优先确认：

- 清理逻辑是否仍正确
- popup 读取是否仍兼容
- 状态字段是否仍能解释

## 文档规则

### 1. 结构性改动建议补文档

以下改动建议补 `docs/`：

- 新增设置项
- 新增 Apifox 行为
- 重构 popup / background
- 调整发布或构建流程

### 2. 文档写法要偏“可执行”

优先写清楚：

- 背景
- 问题
- 原因
- 方案
- 边界
- 后续方向

避免写成只有口号没有结论的文档。

## 验证规则

### 1. 默认至少做一项验证

通常优先：

- `pnpm build`

如果任务涉及类型或共享结构，也可补：

- `pnpm exec tsc --noEmit`

### 2. 不隐瞒仓库历史问题

如果验证失败，要分清楚：

- 是本次改动导致
- 还是仓库原本就存在

不要把历史问题包装成“已验证通过”，也不要把无关历史问题误记到本次改动头上。

## 输出规则

AI 在交付结果时，建议说明：

- 改了什么
- 为什么这样改
- 验证了什么
- 还有哪些已知限制

如果做的是重构，最好补一句这次拆分的边界和后续可继续演进的方向。
