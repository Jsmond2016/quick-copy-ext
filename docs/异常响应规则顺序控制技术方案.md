# 异常响应规则顺序控制技术方案

> **编写时间**：2026-06-01；**修改时间**：2026-06-01；**使用模型**：GPT-5 Codex；**用户**：Jsmond2016

---

## 背景

当前插件设置中的“异常响应规则”字段用于配置接口返回异常的判定逻辑。现有实现虽然已经支持 JSON 数组格式，但业务目标进一步明确为：

- 一个接口只命中一条异常规则
- 规则判断顺序完全由用户配置顺序决定

典型配置场景如下：

```json
[
  {
    "label": "无权限",
    "expression": "res.rtn === 403"
  },
  {
    "label": "下拉为空",
    "expression": "res.data?.list?.length === 0 && res.data?.pagination == null"
  },
  {
    "label": "列表为空",
    "expression": "res.data?.list?.length === 0 && res.data?.pagination != null"
  },
  {
    "label": "异常",
    "expression": "res.rtn !== 0"
  }
]
```

如果响应为 `res.rtn === 403`，期望行为是：

1. 先判断“无权限”
2. 命中后立即停止
3. 后续“异常”不再参与判断

因此，本次方案需要将规则语义统一为“按顺序判断，首条命中即停”。

## 现状分析

当前逻辑位于 `src/lib/quick-copy/response-rules.ts`，历史问题主要有两类：

1. 命中结果曾按内部规则重排，而不是按用户配置顺序执行
2. 规则结构曾尝试支持“命中后是否继续”的可选字段，但这会增加配置理解成本

结合当前业务约束，“一个接口只会命中一条规则”已经足够明确，因此继续保留额外的控制字段没有必要。

## 方案目标

本次改造目标如下：

1. 异常响应规则统一使用 JSON 数组格式
2. 规则按数组顺序依次判断
3. 一个接口只会命中第一条满足条件的规则
4. 不再支持额外的“继续匹配”配置项
5. 保持现有表达式语法不变，降低使用成本

## 方案设计

### 配置格式

异常响应规则统一使用如下格式：

```json
[
  {
    "label": "无权限",
    "expression": "res.rtn === 403"
  },
  {
    "label": "异常",
    "expression": "res.rtn !== 0"
  }
]
```

字段定义如下：

| 字段 | 类型 | 必填 | 说明 |
|:----:|:----:|:----:|:----:|
| `label` | `string` | 是 | 规则名称 |
| `expression` | `string` | 是 | 判断表达式 |

### 行为语义

规则按数组顺序依次判断：

1. 从第一条规则开始计算表达式
2. 若未命中，则继续下一条
3. 若命中，则立即返回该规则
4. 后续规则不再继续判断

也就是说，最终命中结果最多只有 1 条。

### 配置约束

本次改造后，异常响应规则只接受 JSON 数组格式。

如果输入不是 JSON 数组，或数组项字段不合法，则直接视为无效配置。

每一项都必须满足：

- `label` 为非空字符串
- `expression` 为非空字符串

## 详细设计

### 类型调整

在 `src/lib/quick-copy/response-rules.ts` 中，规则类型简化为：

```typescript
export interface ResponseErrorRuleEntry {
  label: string;
  expression: string;
}
```

### 解析器改造

`parseResponseErrorRuleConfig` 只支持数组格式解析：

1. JSON 解析结果必须是数组
2. 每项必须是对象，并包含合法的 `label`、`expression`
3. 若任一项不合法，则整体配置校验失败

### 命中逻辑改造

`getMatchedResponseErrorRules` 不再做任何命中结果重排，也不再支持额外控制字段。

改造后逻辑为：

```typescript
const matchedRules: ResponseErrorRuleEntry[] = [];

for (const entry of ruleEntries) {
  if (!evaluateResponseErrorRule(response, entry.expression)) {
    continue;
  }

  matchedRules.push(entry);
  break;
}

return matchedRules;
```

这样可以保证：

- 判断顺序与配置顺序一致
- 一个接口最多命中一条规则

### 校验逻辑改造

`isValidResponseErrorRuleConfig` 除校验表达式可解析外，还需校验：

- `label` 为非空字符串
- `expression` 为非空字符串

### 默认配置调整

默认配置建议使用如下模板：

```json
[
  {
    "label": "接口异常",
    "expression": "res.rtn !== 0"
  }
]
```

### 设置面板文案调整

`src/pages/popup/components/SettingsPanel.tsx` 中“异常响应规则”字段需要同步更新：

- placeholder 使用无额外控制字段的数组示例
- 提示文案明确“按书写顺序判断”
- 提示文案明确“一个接口只会命中第一条满足条件的规则”
- 明确当前仅支持数组格式

## 风险与应对

| 风险 | 影响 | 应对方案 |
|:----:|:----:|:---------|
| 用户误以为可以同时命中多条规则 | 配置预期与实际不一致 | 在设置面板与文档中明确“只命中第一条” |
| 数组项配置错误 | 保存配置失败 | 校验器严格校验 `label` 与 `expression` |
| 顺序调整影响现有异常原因展示 | popup / background 展示顺序变化 | 以“数组顺序即优先级”作为唯一标准 |

## 验证方案

建议覆盖以下验证场景：

1. `403` 场景优先命中“无权限”，不再继续命中“异常”
2. “下拉为空”与“列表为空”可按顺序互斥判断
3. 非数组格式会被拒绝保存
4. popup 保存、导入、重置后规则均能正常显示和校验

## 结论

本方案通过“有序数组 + 首条命中即停”的方式，为异常响应规则提供稳定、可控且简单的判断语义。

它的优点是：

- 规则优先级直观
- 配置结构简单
- 行为稳定
- 能直接解决重叠规则冲突

适合作为当前异常响应规则配置的正式实现方案。
