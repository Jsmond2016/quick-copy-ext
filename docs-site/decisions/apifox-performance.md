# Apifox 性能优化

## 背景

在插件支持 Apifox 接口映射后，用户反馈 popup 打开明显变慢。

当前使用场景中，Apifox 本地导出的 OpenAPI 数据量较大，默认可能包含约 2000 个接口。popup 每次打开时如果触发了 Apifox 数据准备流程，会带来明显的等待感。

## 根因分析

问题不只是"Apifox 数据大"，而是 popup 生命周期里做了不该在首屏做的工作：

1. popup 初始化时会主动检查并在必要时刷新 Apifox 数据
2. popup 侧存在本地 fallback 逻辑，可能再次执行 `fetch → response.json() → 遍历 paths → 构建映射`

在最差情况下，用户每次打开 popup，都可能触发大 JSON 的网络读取、JSON 解析、全量遍历、中间对象构建。

## 优化方案

### 1. 只保留最小索引结构

不保留完整 schema，只保留两个内存索引：

- `endpointMap`：方法+路径 → Apifox URL
- `pathMap`：路径 → Apifox URL

### 2. popup 启动只读取状态

popup 初始化时不再主动刷新 Apifox 数据，只读取后台已有缓存状态：

- 已就绪则显示缓存条数
- 未就绪则提示手动刷新或保存配置

### 3. 去掉 popup 端的大对象 fallback

popup 不再自己维护 Apifox 缓存和承担大数据解析职责，避免重复内存占用和解析。

### 4. 解析阶段直接构建索引

遍历 schema 时直接写入 Map，跳过中间数组，降低峰值内存和遍历成本。

### 5. 保存配置后后台异步刷新

先立即保存设置 → 关闭面板 → 后台异步刷新 Apifox → 刷新完成后更新状态提示。

## 结论

> popup 是高频打开的交互入口，任何重量级数据准备工作都不应该放在 popup 首屏路径中。

正确做法同时满足三点：

- 数据结构最小化
- 计算时机后移
- 重任务异步化
